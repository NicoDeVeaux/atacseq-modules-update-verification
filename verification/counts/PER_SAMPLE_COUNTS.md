# Per-sample consensus counts: dev vs modules-update (branch → pr448)

Consensus featureCounts read counts for the **HIV MDDC (GRCh38)** cohort, compared
between upstream `dev` and the `nf-core-modules-update` branch. Generated by
`../scripts/compare_featurecounts.py` from the committed count matrices under
`dev/`, `branch/`, and `pr448/`. Totals are summed over the consensus intervals
shared by exact coordinate between each pair of arms.

## TL;DR — the 1.9× inflation is fixed on the current head

The ~1.92× count inflation was real, but it lived on the **commit originally tested**
(`0116142`/`52836f0`), which shipped **subread v2.1.1**. The **current PR #448 head**
(`5caa50bf`) pins subread back to **v2.0.1**; on that head the consensus counts match
`dev` to **within <0.1%** (per-sample ratios 1.000–1.001×). See `pr448` below.

## What this means

**On the originally-tested commit (subread v2.1.1) every sample's counts roughly
doubled** (consistent ~1.92×), while Pearson r ≈ 0.9996 showed a near-uniform
proportional scaling rather than random change. Both arms called featureCounts with
identical flags (`-F SAF -O --fracOverlap 0.2 -p -s 0`) and neither passed
`--countReadPairs`.

**Confirmed cause — the subread `-p` semantics change.** In subread **< 2.0.2**
(dev's v2.0.1) `-p` counts *fragments* (read pairs). From subread **2.0.2 onward**
(v2.1.1) `-p` only declares paired-end input and counts *individual reads* unless
`--countReadPairs` is added. The ~1.92× inflation matches counting both mates instead
of one fragment. Confirmed two ways:

1. **Matrix headers.** All three count matrices record their full `featureCounts`
   command line, byte-for-byte identical except the version — same
   `-F SAF -O --fracOverlap 0.2 -p -s 0`, no `--countReadPairs` anywhere:
   ```
   dev:    featureCounts v2.0.1 ... -F SAF -O --fracOverlap 0.2 -p -T 6 ... -s 0
   branch: featureCounts v2.1.1 ... -F SAF -O --fracOverlap 0.2 -p -T 6 ... -s 0
   pr448:  featureCounts v2.0.1 ... -F SAF -O --fracOverlap 0.2 -p -T 6 ... -s 0
   ```
   Identical flags, identical inputs → the subread version is the only variable.

2. **Direct re-run.** Running subread **v2.1.1** featureCounts on a real paired-end
   BAM both ways confirms the mechanism: `-p` alone reports `Count read pairs: no`
   (counts reads); adding `--countReadPairs` reports `Count read pairs: yes` (counts
   fragments) and roughly halves the assigned total.

**Resolution on the current head (`5caa50bf`, `pr448`).** The subread module is pinned
to `subread:2.0.1--hed695b0_0`, so `-p` again counts fragments and the consensus totals
match `dev`: per-sample ratios 1.000–1.001×, deltas of only +274 to +768 reads
(Pearson r ≈ 0.99995). The residual sub-0.1% differences trace to the consensus interval
set (74,935 vs 74,895; 69,596 shared by exact coordinate) shifting a handful of overlaps,
**not** systematic scaling. This is the parity the PR needed before leaving draft.

> **Note on the fix mechanism.** #448 resolves the inflation by *staying on subread
> v2.0.1* (retaining fragment `-p` semantics), not by adding `--countReadPairs`. Both
> approaches restore fragment-level counts; the pin is the one shipped. If the modules
> update is later re-bumped to subread ≥ 2.0.2, the featureCounts invocation will need
> `--countReadPairs` (e.g. `meta.single_end ? '' : '-p --countReadPairs'`) to keep
> fragment counting. #452 (mixed SE/PE per-batch counting) is orthogonal and produces no
> change on this all-PE cohort.
